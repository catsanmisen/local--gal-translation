# SeaBed：新增行与 CPU 实机验收

2026-10-11，时间为北京时间。结论：**CPU 自动回退和继续显示游戏旁字幕已验证；“只翻译新增行”和延迟目标未通过，当前测试构建不具备发布验收条件。** 玩家无需继续挂机，本轮 50 条对白和 30 分钟连续观察均已完成。

## 实测范围和方法

- 游戏为玩家指定的 `F:\SteamLibrary\steamapps\common\SeaBed\SeaBed.exe`，实际显示日文，窗口化，DPI 200%。使用游戏窗口 WGC 抓帧、Python RapidOCR CPU、GalTransl 4B 真实模型及 WPF 原生字幕；逐条观察游戏、推进对白并人工转录，不用模拟窗口或人工 API 文本代替游戏取词。
- 测试宿主为 `desktop/publish-newrows-qa/GalTransl.Desktop.exe --verification`，API 18079，隔离数据库 `work/seabed-native-test.sqlite3`。没有改写 frontend/、生产数据库、游戏汉化文件或 Magpie 设置。Magpie 按玩家要求不测；本次不代表 HOOK、Ever17 或 BGI 验收。
- verification 构建为观察字幕而使用不同的窗口捕获排除设置；这次未验收正式构建的防自身捕获保证，也未覆盖跨屏/DPI切换。当前单屏200%DPI表现不能代替这些项目。
- 正式样本为人工编号 n27–n77，排除章节卡 n42，合计 **50 条真实对白**。n1–n26 为探索阶段，不混入统计。50 条采样记录时间约 12:39:29–13:13:15。额外保留章节卡失败和迟到检查记录，但不增加对白分母。
- 连续观察独立运行 1800 秒，12:38:56 起；最后一条采样为 13:08:55，距开始 1798.875 秒，随后程序正常结束。两秒采样合计 **890 条**，采样均处于游戏前台、已绑定、CPU 模式，无观察器错误。部分对白在观察窗口结束后完成，不能说全部 50 条都位于这 30 分钟内。
- 正式阶段产品代码冻结；宿主 DLL、core、OCR worker/layout 的前后 SHA256 相同。12:58:05 手动按一次读档重置快捷键测试上下文恢复，epoch 从 1 变 2；模型和构建未重启。n61 为转录被超长字幕遮挡的原文，短暂隐藏后恢复字幕。这不是“全程无需干预”的通过证明。
- 动态壁纸进程保持运行，未修改播放设置或主动停止；壁纸软件自身可能因游戏前台而暂停，不能据此宣称测到了壁纸始终渲染的最高负载。

## CPU 自动回退

采用限时、独立端口的受控 GPU 负载组件触发真实显存监测，没有伪造显存数值或手动设置 CPU 层数。组件由测试工具管理并已全部释放，游戏与壁纸进程未结束。

最新一轮在 **12:29:58** 记录显存不足暂停，**12:30:44** 恢复 ready/CPU，墙钟约 **45.735 秒**。中间设置窗在前台，恢复按前台条件等待；因此这不是连续前台下的纯模型启动耗时。较早探索轮连续前台约 19.8–20.1 秒，但不能用这些轮次替换最新构建的 45.7 秒结果。

恢复后的实际 llama-server 参数为 `--threads 8 --threads-batch 8 --gpu-layers 0 --device none --no-kv-offload`，状态也报告 CPU。正式 50 条均在这一 CPU 模式下；最后 n77 的正确中文译文实际显示在游戏原文上方，推理 2844ms。这验证了自动 CPU 恢复后真实 OCR→模型→原生字幕链路，而不是只检查状态字段。

仍然只验证了受控显存压力；没有证明每种日常资源争用都能恢复。CPU 模式在显存释放后未自动升级 GPU，本轮继续测 CPU。观察期可用显存最低 3309MiB，保持现有 2048MiB 余量。

## 新增行与可用性结果

| 项目 | 实测结果 | 判定 |
|---|---|---|
| 真实对白 | 50 条，48 条获得终态响应，2 条漏捕或稳定超时 | 48 条不等于 48 条正确可用字幕 |
| 累积页面追加 | 40 条追加、10 条新页 | 独立新行可以正确抽取，但不能覆盖所有追加方式 |
| 追加时重复旧原文 | 14/40（35%） | 未通过；同一行增长及旧行多个标点变化会触发整页翻译 |
| 漏捕/稳定超时 | n33、n51，2/50（4%） | 超过既定漏捕≤2%口径；n51 等待超过35秒仍 capturing，迟到检查仍无终态 |
| 短句混入背景碎片 | n27、48、55、69 | 短文本缺少长行锚点时，装饰或人物背景字形进入正文/边界 |
| 提示词或历史回显 | n53、54、61、62，4/48 个终态响应 | 未通过；污染后续上下文，重置后仍可再次发生 |
| 字幕位置与穿透 | 正常短译文可位于原文上方，点击仍能推进游戏 | 超长错误输出会扩大字幕并遮挡原文，不能判整体定位合格 |

新增行对照例：n37、n75 的实际提交文本等于人工转录的新增正文；n28 已把旧省略号一并提交；n53、n61、n74 在原有行末追加后提交了多行整页。n53 推理 13.219 秒、n61 为 20.312 秒，且包含提示词回显。章节卡 n42 另行记录：章节标题漏字，输出旧上下文，未算作50条对白。

还观察到有终态记录后，后续OCR波动再次清除字幕（例如n67）。因此“completed_response”仅表示获得响应，不表示字幕一直可见；本文不提供缺少连续画面证据的“正确字幕率”。

提交正文对人工新增正文的编辑率为 **69.19%**，包含重复旧行及两条缺失；这是取词与增量选择的组合错误率，**不是原始 OCR CER**。未持久化全部原始 OCR 帧/结果，不能伪称已计算50条原始 OCR CER或满足≤5%。即使暂不使用这个编辑率，漏捕和重复已足以判定不合格。14 次重复也不等同于“同一请求重发”；属于增量选择把旧内容重新送入新请求。

## CPU 实际延迟

48 个完成响应纳入统计，含错误和回显输出，不挑选快句。两条未完成对白不计入有限耗时分位数，单独报告超时；不能把它们当成0ms。P95 使用 nearest-rank，n=48。

| 阶段 | 中位数 | P95 | 最大值 |
|---|---:|---:|---:|
| 抓帧 capture_ms | 96ms | 119ms | 153ms |
| OCR ocr_ms | 758ms | 1281ms | 1438ms |
| 稳定等待 stable_wait_ms | 833ms | 1433ms | 1613ms |
| 推理排队 queue_ms | 0ms | 0ms | 16ms |
| 完整推理 inference_ms | **2.578s** | **13.219s** | 25.250s |
| 稳定原文→原生字幕事件/Dispatcher 更新 | **2.621s** | **13.241s** | 25.313s |
| 首次抓帧→原生更新（阶段相加近似值） | **4.446s** | **15.509s** | 28.104s |

原生日志记录最终事件接收和 Dispatcher 更新，未单独测量屏幕像素绘制时刻；最后一行是同一请求各阶段相加的近似值，不含游戏点击到首次抓帧的轮询等待。稳定等待中包含后续识别轮次，所以不是固定300/600ms。稳定原文到完整字幕的 **中位≤1.5s、P95≤3s目标均未达到**；尚未绘制的事件时刻已经超标。原始响应中的最小281ms是错误短输出，不能作为可用字幕性能宣传。

主要瓶颈是 CPU 整段生成、整页重复和提示词回显；OCR及稳定等待本身也约占1.6秒的中位开销。此次样本不能外推为所有游戏/所有CPU的速度。

## 回归与未通过项

本轮后端77、原生逻辑24、连接层7、前端Mock22、SSE4，合计 **134项通过**，包含原80项基线。frontend/没有写入；回归通过不抵消实机失败。当前测试目录未提升为正式发布包。

下一轮必须先修复增量选择（同一行续写及标点漂移）、短句正文范围、提示词/历史回显的拒收与上下文隔离、超长字幕高度限制，再用新构建重新采样验收。纯增加前缀容错或放宽输出校验会误删真实文字/放行异常输出，不能作为通过依据。CPU延迟需要分别优化识别轮次和有效新增正文的推理长度，不能把当前P95更改口径后宣布达标。
